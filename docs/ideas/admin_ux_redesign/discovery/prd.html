Visão Geral

Criar um plano não pode dar preguiça

O admin web é a fábrica de planos do Forja: é lá que fichas viram treinos que o app sincroniza. Hoje, porém, a experiência de criação trava o próprio dono — o form de novo plano assusta com 9 campos, a importação de fichas esconde se aceita 1 ou várias, e o caminho "rascunho → publicado no app" espalha 4 gestos por 3 lugares diferentes da tela. A auditoria de código encontrou o motivo: não existe botão "Adicionar exercício" no editor — montar um plano manual pela UI é literalmente impossível hoje.

Este PRD redesenha a experiência core do admin em torno de uma ideia: criar plano = abrir o editor. Um hub de criação substitui o form assustador (em branco, da foto, ou duplicando um plano); a foto da ficha vira rascunho direto no editor; salvar fica barato (autosave) e publicar é o único gesto que afeta o app — e nunca é silencioso. Inspirado no modelo Vercel/Webflow: rascunho é workspace, publicar é promoção de revisão.

Problema

Por que dá preguiça

Beco sem saída: não dá para montar plano manual

O editor só lista exercícios existentes — o service layer não tem addDraftExercise e nenhum botão de adicionar existe. As únicas portas de entrada de exercícios são o 1º exercício obrigatório do form de novo plano e a importação por IA. Resultado: todo plano real nasce de foto, e o import carrega sozinho o peso de ser o único caminho.

O form de novo plano assusta

9 campos (5 obrigatórios + 4 escondidos num disclosure) para gerar um plano de um único exercício. "Rótulo" vs "Nome" sem diferença explicada (o rótulo é um slug de implementação que vazou para a UI). O domínio, no entanto, aceita plano com zero exercícios — toda essa fricção é imposta pela UI, não pelo schema.

Publicar pode publicar conteúdo velho

"Salvar rascunho" e "Publicar no app" são forms independentes em lugares diferentes da tela. Publicar usa o draft persistido no banco — se você editou e não salvou, a versão antiga é publicada em silêncio. Sem guard, sem aviso, sem confirmação do que foi publicado.

Importar: 1 ou várias fichas?

O campo diz "Nome da ficha" (singular), mas o input aceita N imagens e cada uma vira uma ficha com numeração-surpresa ("Treino A 1, 2, 3…") que só aparece depois da extração. A revisão é read-only — corrigir um erro da IA exige salvar, abrir o editor, editar e salvar de novo. E o stepper promete uma etapa "Publicar" que não existe naquela tela.

Três nomes para o mesmo estado — e um KPI que mente

Painel, lista e editor batizam a pendência de três jeitos. O KPI "Publicação pendente" conta apenas planos nunca publicados: um plano publicado com edições não publicadas fica invisível no painel. Para um produto de um único admin, estado invisível é estado que não existe.

Princípios

As regras do admin daqui em diante

  1. O editor é a única tela de autoria. Criar plano = abrir o editor. Nenhum form intermediário entre a intenção e a lista de exercícios.
  2. Publicar é o único gesto que afeta o app — e nunca é silencioso. Salvar é barato; publicar é explícito e sempre responde "o que o app está treinando agora".
  3. Nenhum dado velho se publica. Publicar sempre inclui as edições correntes; formulário sujo não existe como estado publicável.
  4. Defaults em vez de campos obrigatórios. "A definir" é um valor válido. O form pede só o que só o humano sabe.
  5. Uma imagem = uma ficha — regra visível antes de agir. Batch declarado na entrada, nunca descoberto depois.
  6. A revisão editável acontece na hora. O momento mais barato de corrigir a IA é durante a revisão; confiança baixa vira destaque com ação, não percentual decorativo.
  7. Vocabulário único de estado: Rascunho · Publicado · Publicado com alterações · Arquivado. "Draft" é proibido em copy pt-BR.
  8. Toda lista tem um CTA que diz a próxima ação ("Revisar e publicar"), não o nome da tela.

Por que isso é seguro

O app móvel só enxerga a última revisão publicada de cada plano ativo (planPullService, pull cursor-based; arquitectura vira tombstone). Rascunho é 100% invisível para o consumidor — criar rascunhos "de teste" ou "da IA" tem custo zero no app. O modelo já era certo; a comunicação é que falhava.

Antes: 0 possíveis pela UI

Depois: criação manual se torna caminho comum; import deixa de ser rota obrigatória

Tempo ideia → publicado

Antes: ~8 ações + becos sem saída

Antes: ~20 interações para 4 fichas, revisão read-only

Riscos

O que pode dar errado

Poluição da lista com rascunhos da IA

Médio

Foto → rascunho imediato pode encher a lista de fichas descartáveis se a extração for ruim.

Mitigação: badge "Importado — revise" com filtro próprio na lista; arquivar em 1 clique por card; rascunhos não publicados nunca tocam o app. Se virar problema real: limpeza em lote (backlog).

Autosave com falha parcial

Médio

Salvar campo-a-campo com debounce pode deixar estados intermediários (um exercício salvo, outro não) se a rede falhar no meio.

Mitigação: estado de save por grupo (plano vs exercício), retry manual na barra, e "Salvar agora" como escape. Admin único elimina conflito de concorrência. Publicar continua sendo transação composta atômica.

Perder o gate de revisão pré-criação do import

Baixo

Hoje a revisão acontece antes de criar qualquer coisa; na proposta, cria-se primeiro e revisa depois.

Mitigação: decisão consciente (reversibilidade > gate para um admin dono do dado): rascunho é invisível ao app, descarte continua em dois passos, e a edição no editor é mais barata que na tela de review atual.

Escopo crescer para redesign visual

Médio

Redesign de fluxo pode virar redesign de design system (tokens, componentes) e nunca sair.

Mitigação: este PRD muda fluxos e copy usando o vocabulário visual existente (.admin-*); o polish de design system é trilha paralela (tokens, ícones, feedback async) já mapeada em relatório próprio.

Considerações Técnicas

O que já existe vs o que falta

Já existe (só UI em cima)

  • Criação server-side de draft: createDraftPlan no planService
  • Updates granulares: updateDraftExercise, updateDraftPlanDetails, reorderDraftExercises
  • Revisões: publishDraftPlan cria linha em plan_revisions — publicar como promoção é o modelo atual
  • Domínio permissivo: PlanSchema sem mínimo de exercícios; equipment aceita vazio
  • Isolamento do app: sync pull-based só serve última revisão publicada; rascunho nunca vaza
  • Extração por IA: endpoint de extract + criação de planos a partir da extração (batch com createBatchLabel)

Novo (TDD)

  • Service: addDraftExercise, removeDraftExercise, duplicatePlan, diff de revisões, contagem correta de pendências na listagem
  • Actions: publicar composto (update + publish atômico), criar-em-branco (1 clique), importar→rascunho com marcação de confiança
  • UI: hub de criação, barra fixa do editor, "+ Adicionar exercício", estados de autosave, badges de import, notice pós-publish
  • Sem migração de schema — tudo cabe no modelo atual (marcação de confiança da IA pode viver no draft como metadado transitório ou ser só visual na sessão)

Guardrails de UX (testes)

  • Teste de contrato: publicar com form sujo publica o que está na tela (nunca o draft velho)
  • Teste de copy: vocabulário de estado idêntico nas 3 superfícies; zero "draft" em pt-BR
  • Teste de KPI: pendência conta nunca-publicados + com-alterações
  • Teste de import: N imagens declara N fichas antes do envio
Fora do Escopo (v1)

O que NÃO está incluído

  • Undo de publicação ("republish Rev. N−1") — os dados existem em plan_revisions; fica para v2
  • Templates de plano — "Duplicar" cobre o caso de uso de um admin único
  • Biblioteca de exercícios com busca — v1 mantém campo livre + categoria; biblioteca quando o volume doer
  • Edição colaborativa / multi-usuário — admin é único por design
  • Cmd-K, toasts globais, skeletons de rota — rejeitados no benchmark para um admin de 3 telas e DB local
  • Redesign visual / design system — trilha paralela (tokens, ícones, feedback async), fora deste PRD
